***Conceitos de performance***

Para definir o desempenho de um ambiente do SQL, podemos medir o tempo de resposta para uma solicitação ao banco de dados, como uma consulta, a execução de um stored procedure (procedimento armazenado), ou o envio de um comando complexo.

Muitos fatores influenciam no tempo de resposta, alguns não gerenciáveis pelo DBA, mas é importante que ele seja capaz de identificá-los e melhorar o desempenho. Devemos monitorar e ajustar muitos outros fatores que possam afetar o desempenho, além do tempo de resposta.

***Quantidade de solicitações***<br>
A quantidade de solicitações inclui o número de consultas e transações por segundo, além do número de pessoas usuárias que acessam o banco de dados simultaneamente.

***Espaço afetado pelas solicitações***<br>
Outro ponto importante é o espaço em disco afetado pelas solicitações. A falta de espaço pode resultar em diversos problemas, incluindo lentidão do sistema, interrupção de operações e perda de dados. Portanto, é importante monitorar o uso do espaço em disco, incluindo o tamanho total do banco, das tabelas, de índices, e dos arquivos de log.

***Tipos de solicitações***<br>
Os tipos de solicitações que os usuários fazem no ambiente do SQL Server também são importantes, pois cada tipo de operação tem um impacto diferente na performance do sistema.<br>
Por exemplo: operações de inserção, atualização e exclusão são mais intensivas em I.O.U. do que consultas. Por outro lado, consultas que exigem somas e agregações podem ser mais intensivas em CPU e memória e afetar a performance.

***Dificuldade de solicitações***<br>
Por fim, conhecer a complexidade das solicitações é fundamental para garantir o desempenho em uma instância do SQL Server.

Solicitações simples, como a leitura de uma tabela, têm menos impacto na performance do sistema do que solicitações mais complexas, como as que fazem joins entre tabelas, que podem ser mais intensivas em CPU e memória, afetando negativamente a performance do SQL Server.

***Active monitor***<br>
O Active Monitor é a ferramenta que o DBA tem à disposição para analisar essa linha base no ambiente do SQL Server. Ele serve para monitorar e diagnosticar o servidor do Microsoft SQL Server. Essa é uma ferramenta projetada para fornecer ao DBA informações detalhadas sobre a saúde e o desempenho do banco de dados, a fim de ajudar a identificar rapidamente quaisquer problemas que possam estar afetando o desempenho do banco de dados.

O Active Monitor é composto de várias componentes, incluindo:<br>

- Coletor de dados;
- Serviço de gerenciamento;
- Interface de usuário.

***SQL Server Profiler***<br>

O **SQL Server Profiler** é uma ferramenta essencial para monitorar e analisar o desempenho de consultas SQL. Vamos explorar seu funcionamento com alguns exemplos práticos.

## Configuração do Profiler

Inicialmente, ao ligar o Profiler, ele não registra nada porque configuramos um filtro para capturar apenas consultas enviadas pelo usuário **SA**.

## Executando Consultas e Acompanhando no Profiler

### Consulta de Produtos
```sql
SELECT codigo_produto AS PRODUTO, produto AS NOME_PRODUTO
FROM [dbo].[tb_produto];
```
Ao executar essa consulta, o Profiler registra quatro linhas, incluindo:
- **SQL: BatchStarting**: Indica o início da execução da consulta.
- **TextData**: Contém o código SQL enviado.
- **CPU e Duration**: Mostram o impacto da consulta em termos de processamento e tempo.
- **Reads e RowCounts**: Informam a quantidade de dados lidos e retornados.

### Consulta de Estados
```sql
SELECT sigla_estado AS ESTADO, nome_estado AS NOME_ESTADO FROM tb_estado;
```
Esta consulta retornou menos linhas e, consequentemente, levou menos tempo para ser processada.

### Consulta em Tabela Grande
```sql
SELECT * FROM [dbo].[tb_cliente];
```
Dado que a tabela **tb_cliente** contém 1 milhão de registros, essa consulta levou **7 segundos** para ser concluída. O Profiler mostrou:
- **Leituras: 12.648**
- **Linhas retornadas: 1 milhão**
- **Duração: 7.612 segundos**

Isso destaca o impacto do volume de dados na performance.

## Consultas de Processamento Pesado

Agora, executamos uma consulta mais complexa, envolvendo múltiplos joins e agregações:
```sql
SELECT dbo.tb_estado.nome_estado AS ESTADO, dbo.tb_produto.produto AS PRODUTO, YEAR([data]) AS ANO,
         SUM(CONVERT(FLOAT, (dbo.tb_item.quantidade))) AS QUANTIDADE
FROM dbo.tb_item
INNER JOIN dbo.tb_produto ON dbo.tb_item.codigo_produto = dbo.tb_produto.codigo_produto
INNER JOIN dbo.tb_nota ON dbo.tb_item.numero = dbo.tb_nota.numero
CROSS JOIN dbo.tb_cliente
INNER JOIN dbo.tb_cidade ON dbo.tb_cliente.cidade = dbo.tb_cidade.cidade
INNER JOIN dbo.tb_estado ON dbo.tb_cidade.sigla_estado = dbo.tb_estado.sigla_estado
WHERE dbo.tb_produto.codigo_produto = 2
AND dbo.tb_estado.sigla_estado = 'RJ'
AND YEAR([data]) = 2020
GROUP BY dbo.tb_estado.nome_estado, dbo.tb_produto.produto, YEAR([data]);
```
Essa consulta demorou **7 segundos**, mas por motivos diferentes:
- **Alta carga de processamento**: Trabalhou com **344.170 linhas** e retornou apenas **3 linhas**.
- **Anteriormente, o tempo foi gasto na escrita dos dados retornados; aqui, foi gasto no processamento interno**.

## Simulação de Múltiplas Consultas

Para monitorar consultas simultâneas, ativamos o **Monitor de Atividades**:
1. Clique com o botão direito no **Desktop** dentro do **Management Studio**.
2. Selecione **Monitor de Atividades**.
3. O SQL Server Profiler começará a capturar várias consultas do ambiente.
4. Ao fechar a aba do **Monitor de Atividades**, as capturas são interrompidas.

Esse monitoramento é essencial para otimizar consultas e garantir um desempenho eficiente do banco de dados.

## Uso do Trace no SQL Server

O **trace** não deve ser mantido ligado o tempo todo, pois consome processamento ao registrar todas as operações executadas no SQL Server. Ele deve ser ativado apenas quando o **Monitor de Atividades** indicar que há um desvio no comportamento normal do banco de dados.

Quando o DBA percebe um aumento anormal no consumo de recursos, ele pode ativar o **trace** para identificar qual consulta ou operação está causando o problema. Assim que a investigação for concluída, o **trace** deve ser desativado para evitar impacto no desempenho do sistema.

### Vantagens do Uso de Modelos de Trace

- **Economia de tempo**: Ao salvar um modelo de evento com as configurações mais utilizadas, o usuário não precisa reconfigurar o SQL Server Profiler toda vez que precisar monitorar um evento.
- **Consistência**: Um modelo salvo garante que as configurações de eventos e colunas monitoradas sejam padronizadas, evitando erros e variações na coleta de dados.
- **Repetitividade**: Com um modelo salvo, é possível repetir o mesmo perfil de monitoramento várias vezes, útil para testes de desempenho e detecção de problemas recorrentes.
- **Facilidade de compartilhamento**: Um modelo salvo pode ser compartilhado com outros membros da equipe ou departamentos, garantindo padronização na coleta de dados e facilitando a colaboração.
- **Personalização**: As configurações de eventos e colunas podem ser ajustadas conforme as necessidades do usuário, permitindo um monitoramento mais preciso e eficiente.

### Como Criar e Utilizar um Modelo de Trace

1. **Salvar o TRACE do exercício anterior como um modelo**.
2. **Fechar o Trace atual**.
3. **Criar um novo TRACE utilizando o modelo salvo**.

Com essa abordagem, o monitoramento do SQL Server se torna mais eficiente e padronizado, facilitando a análise e detecção de problemas no ambiente.

## Módulos do SQL Server Profiler

- **Eventos**: Define quais eventos do SQL Server serão monitorados (inserções, atualizações, consultas, etc.).
- **Colunas**: Permite especificar informações a serem visualizadas, como tempo de execução, leituras e escritas.
- **Templates**: Configurações salvas para uso futuro, facilitando a geração de relatórios.
- **Filtros**: Permitem filtrar resultados por data, usuário ou eventos, garantindo rastreamento mais específico.
- **Gráficos e Relatórios**: Possibilita salvar o conteúdo do trace em tabelas e construir relatórios detalhados.
- **Armazenamento de Seções**: Salva temporariamente informações coletadas para análise posterior.

## Comandos T-SQL para SQL Server Profiler

- `sp_trace_create`: Cria uma nova seção de rastreamento.
- `sp_trace_setevent`: Configura os eventos a serem capturados.
- `sp_trace_setfilter`: Aplica filtros ao rastreamento.
- `sp_trace_start`: Inicia a seção de rastreamento.
- `sp_trace_stop`: Interrompe ou finaliza o rastreamento.
- `sp_trace_delete`: Exclui uma seção de rastreamento.
- `sp_trace_getdata`: Recupera dados capturados durante o rastreamento.

Esses comandos podem ser usados para automatizar a coleta de trace em determinados períodos via T-SQL.

# Índices no Banco de Dados

Os índices são estruturas auxiliares que otimizam a busca por registros, reduzindo o tempo de execução das consultas.

## 🚀 Como Funciona?

Sem um índice, o SQL Server executa um **Table Scan**, percorrendo linha a linha da tabela para encontrar os dados. Isso pode tornar a busca lenta, especialmente em tabelas grandes.

### 🔍 Exemplo de Consulta Sem Índice:
```sql
SELECT * FROM tb_cliente WHERE cidade = 'Salvador';
```
O plano de execução indicará um **Table Scan**, pois a tabela não tem um índice sobre a coluna `cidade`.

## 📌 Criando um Índice

Podemos criar um **índice não clusterizado** para melhorar a performance da consulta:

```sql
CREATE NONCLUSTERED INDEX idx_tb_cliente_cidade 
ON tb_cliente (cidade) 
INCLUDE (cpf, nome, sobrenome, email, telefone, numero, rua, complemento);
```

### 📊 Benefícios:
- O banco de dados utilizará um **Index Seek** em vez de **Table Scan**.
- A busca será mais eficiente, pois o índice é estruturado para localizar rapidamente os registros.

## 🏗️ Estrutura do Índice

O índice funciona como uma tabela auxiliar ordenada, permitindo que a busca seja feita com um algoritmo otimizado.  

Exemplo de organização de um índice:

| CLIENTE | LINHA |
|---------|------|
| 001     | 2    |
| 002     | 1    |
| 003     | 3    |

Isso permite encontrar rapidamente a posição do registro na memória, agilizando a consulta.

## 🔄 Índice Clusterizado vs. Não Clusterizado

- **Índice Clusterizado:** Os dados da tabela são armazenados diretamente na ordem do índice.
- **Índice Não Clusterizado:** Existe uma estrutura separada que referencia os registros da tabela.

Embora o **índice clusterizado** seja mais eficiente, ele deve ser utilizado com cautela, pois apenas um pode existir por tabela.

# Índices no SQL Server

## Como escolher o índice correto?

Para entender qual índice deve ser usado dependendo da consulta, siga os passos abaixo.

### Baixando o arquivo

Baixe o arquivo `ConsultasIndices.sql` disponibilizado na atividade "Preparando o ambiente".

### Abrindo no SQL Server Management Studio

1. Abra o SQL Server Management Studio.
2. No menu superior, vá em **"Arquivo > Abrir > Arquivo"** (atalho **"Ctrl + O"**).
3. Selecione o arquivo `ConsultasIndices.sql` e clique em **"Abrir"**.

### Criando a tabela e inserindo registros

Crie a tabela `T_heap` com os seguintes campos:

```sql
DROP TABLE IF EXISTS T_heap;
CREATE TABLE T_heap (
    a INT NOT NULL,
    b INT NOT NULL,
    c INT NOT NULL,
    d INT NOT NULL,
    e INT NOT NULL,
    f INT NOT NULL
);
```

Agora, insira 50 registros com valores aleatórios para os campos `a` até `e` e um contador no campo `f`:

```sql
declare @contador int
declare @max int
SET @contador = 1
SET @max = 50

WHILE @contador <= @max
BEGIN
    INSERT INTO T_heap (a, b, c, d, e, f) 
    VALUES ([dbo].[NumeroAleatorio](1,100), [dbo].[NumeroAleatorio](1,100),
            [dbo].[NumeroAleatorio](1,100), [dbo].[NumeroAleatorio](1,100),
            [dbo].[NumeroAleatorio](1,100), @contador);
    SET @contador = @contador + 1;
END
```

Para visualizar os dados:

```sql
SELECT * FROM T_heap;
```

---

## Consulta com Índice Não Clusterizado

Sem um índice, o SQL Server faz um `Table Scan`, percorrendo todas as linhas:

```sql
SELECT b, c FROM T_heap WHERE b = 68 AND c = 55;
```

### Criando um índice não clusterizado

Criamos um índice para o campo `a`:

```sql
CREATE NONCLUSTERED INDEX T_heap_a ON T_heap (a);
```

Se consultarmos o campo `b`, o índice não será utilizado:

```sql
SELECT b FROM T_heap WHERE b = 1;
```

Agora, se consultarmos `a`, o índice será utilizado:

```sql
SELECT a FROM T_heap WHERE a = 1;
```

Criando um índice para `b` e `c`:

```sql
CREATE INDEX T_heap_bc ON T_heap (b, c);
```

Agora, consultas que usam `b` e `c` como critério utilizarão o índice:

```sql
SELECT b, c FROM T_heap WHERE b = 1 AND c = 1;
```

Se consultarmos `a` filtrando por `b` e `c`, o índice **não será utilizado**:

```sql
SELECT a FROM T_heap WHERE b = 1 AND c = 1;
```

Isso ocorre porque não existe um índice que contenha `a, b e c` juntos.

---

## Cláusula INCLUDE

Criamos um índice para `d` e incluímos `e` com `INCLUDE`:

```sql
CREATE INDEX T_heap_d ON T_heap (d) INCLUDE (e);
```

Isso permite que consultas que envolvem `d` e `e` utilizem o índice:

```sql
SELECT d, e FROM T_heap WHERE d = 1 AND e = 1;
```

Se consultarmos apenas `e`, o índice também será utilizado:

```sql
SELECT e FROM T_heap WHERE d = 1 AND e = 1;
```

Mas, se consultarmos `a` filtrando por `d` e `e`, o SQL Server fará um `Table Scan`:

```sql
SELECT a FROM T_heap WHERE d = 1 AND e = 1;
```

Para resolver isso, incluímos `a` no índice:

```sql
DROP INDEX T_heap_d ON T_heap;
CREATE INDEX T_heap_d ON T_heap (d) INCLUDE (e, a);
```

Agora, essa consulta utilizará o índice:

```sql
SELECT a FROM T_heap WHERE d = 1 AND e = 1;
```
